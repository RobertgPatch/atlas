# Data Model: TIC Registry Page

## Overview

The TIC Registry stores a nested ownership record:

1. A TIC property is the top-level registry record.
2. A TIC property has many TIC interests, where each interest represents the TIC/LLC that owns a percentage of the property.
3. A TIC interest has many underlying owners with percentages of that TIC/LLC.
4. Exchange-acquired TIC interests may reference a prior interest or a manual relinquished source.

The API returns nested records plus derived summary and allocation fields. The database stores canonical records and timestamps.

## Entity: TIC Property

**Table**: `tic_properties`

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `id` | uuid | yes | Primary key, generated by database |
| `name` | text | yes | Property name or address, trimmed, 1-200 chars |
| `property_type` | text | yes | One of `multifamily`, `retail`, `office`, `industrial`, `self_storage`, `hospitality`, `land`, `mixed_use`, `other` |
| `status` | text | yes | One of `held`, `under_contract`, `sold`; default `held` |
| `acquired_date` | date | no | Must not be an invalid date |
| `estimated_value_usd` | numeric(18,2) | no | Must be >= 0 when present |
| `notes` | text | no | Max 10,000 chars |
| `created_by_user_id` | uuid | no | References `users(id)` with `on delete set null` |
| `updated_by_user_id` | uuid | no | References `users(id)` with `on delete set null` |
| `created_at` | timestamptz | yes | Defaults to now |
| `updated_at` | timestamptz | yes | Updated on mutation |

**Relationships**:

- Has many `tic_interests`.
- Deleting a property cascades to its interests and owners after user confirmation.

**Indexes**:

- `(lower(name))` for search.
- `(status)` for filters and summary.

## Entity: TIC Interest

**Table**: `tic_interests`

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `id` | uuid | yes | Primary key, generated by database |
| `property_id` | uuid | yes | References `tic_properties(id)` with `on delete cascade` |
| `name` | text | yes | TIC/LLC name, trimmed, 1-200 chars |
| `property_percentage` | numeric(9,4) | yes | 0 through 100 |
| `status` | text | yes | One of `active`, `rolled`, `exited`; default `active` |
| `acquisition_origin` | text | yes | One of `cash`, `exchange` |
| `relinquished_interest_id` | uuid | no | References `tic_interests(id)` with `on delete set null`; cannot equal `id` |
| `relinquished_source_name` | text | no | Manual source label when source is not in registry |
| `relinquished_source_label` | text | no | Snapshot label preserved for display if referenced source is removed |
| `acquisition_date` | date | no | Exchange or purchase date |
| `acquisition_value_usd` | numeric(18,2) | no | Must be >= 0 when present |
| `notes` | text | no | Max 10,000 chars |
| `created_by_user_id` | uuid | no | References `users(id)` with `on delete set null` |
| `updated_by_user_id` | uuid | no | References `users(id)` with `on delete set null` |
| `created_at` | timestamptz | yes | Defaults to now |
| `updated_at` | timestamptz | yes | Updated on mutation |

**Relationships**:

- Belongs to one `tic_properties` row.
- Has many `tic_owners`.
- May reference another TIC interest as its exchange source.

**Validation rules**:

- `acquisition_origin = cash` does not require a relinquished source.
- `acquisition_origin = exchange` should include either `relinquished_interest_id` or `relinquished_source_name`.
- When a new exchange interest references an active source interest, the service marks the source interest `rolled` in the same transaction.
- A referenced source interest must exist in the registry and cannot reference itself.

**Indexes**:

- `(property_id)`.
- `(relinquished_interest_id)`.
- `(property_id, lower(name))` for duplicate detection/search.

## Entity: TIC Owner

**Table**: `tic_owners`

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `id` | uuid | yes | Primary key, generated by database |
| `tic_interest_id` | uuid | yes | References `tic_interests(id)` with `on delete cascade` |
| `name` | text | yes | Owner name, trimmed, 1-200 chars |
| `owner_type` | text | yes | One of `individual`, `llc`, `trust`, `partnership`, `s_corp`, `ira`, `other` |
| `tic_percentage` | numeric(9,4) | yes | 0 through 100 |
| `created_by_user_id` | uuid | no | References `users(id)` with `on delete set null` |
| `updated_by_user_id` | uuid | no | References `users(id)` with `on delete set null` |
| `created_at` | timestamptz | yes | Defaults to now |
| `updated_at` | timestamptz | yes | Updated on mutation |

**Relationships**:

- Belongs to one `tic_interests` row.

**Derived fields**:

- `effective_property_percentage = interest.property_percentage * owner.tic_percentage / 100`.

**Indexes**:

- `(tic_interest_id)`.
- `(tic_interest_id, lower(name))` for duplicate detection/search.

## Derived Response: TIC Registry Summary

Returned with list responses.

| Field | Type | Notes |
|-------|------|-------|
| `propertyCount` | integer | Count of visible properties |
| `ticInterestCount` | integer | Count of visible TIC interests |
| `ownerCount` | integer | Count of visible owners |
| `estimatedHeldValueUsd` | number | Sum of visible property values where status is not `sold` |
| `underAllocatedPropertyCount` | integer | Properties where interest total is below 100 |
| `overAllocatedPropertyCount` | integer | Properties where interest total is above 100 |
| `underAllocatedInterestCount` | integer | TIC interests where owner total is below 100 and owners exist |
| `overAllocatedInterestCount` | integer | TIC interests where owner total is above 100 |

## Derived Response: Allocation Status

Allocation status is calculated, not stored.

| Input | Status | Display |
|-------|--------|---------|
| Sum within 0.01 of 100 | `ok` | `100% allocated` |
| Sum below 100 by 0.01 or more | `under` | Shows allocated percent and unassigned percent |
| Sum above 100 by 0.01 or more | `over` | Shows allocated percent and overage |

## State Transitions

### Property Status

```text
held -> under_contract -> sold
held -> sold
under_contract -> held
sold -> held or under_contract only through Admin edit
```

The UI should not block corrections, but it should clearly display sold properties as excluded from estimated held value.

### TIC Interest Status

```text
active -> rolled
active -> exited
rolled -> active only through Admin correction
exited -> active only through Admin correction
```

When an active source interest is referenced by a new exchange interest, the service should update the source to `rolled` in the same transaction.

## Delete Behavior

- Deleting a property deletes its TIC interests and owners.
- Deleting a TIC interest deletes its owners.
- Deleting an owner only removes that owner.
- When a deleted TIC interest is referenced as an exchange source, the referencing row keeps `relinquished_source_label`; the foreign key becomes null.
- All destructive actions require confirmation in the UI.

## API Validation Summary

- Required names must be non-empty after trimming.
- Percentages must be finite numbers from 0 to 100 inclusive, with at most four decimal places.
- Dollar values must be finite numbers >= 0, with at most two decimal places.
- Date fields must be ISO `YYYY-MM-DD`.
- Text notes are capped at 10,000 chars.
- Mutations must verify Admin role before writing.
- Patch/delete operations should accept `expectedUpdatedAt` to return a stale-update error when the record changed since the user opened it.
